# S4 — Offline Search Design

**Status:** Design spec (pre-implementation)  
**Session:** 2026-06-13  
**Follows:** Phase 2 PWA (manifest + SW + offline reader — complete)  
**Implements:** Phase 3 (offline search) from `docs/PHASE2_PLAN.md`

---

## 1. Goal

After Phase 2 an installed PWA can cache individual source pages for offline reading. Phase 3 extends that: the user can run full-corpus text search with no network, using the same query modes the server supports (plain, FTS5, case-sensitive, whole-word, regex, SLP1). Morphological / stem search stays network-only because it needs the Python stemmer.

---

## 2. Engine choice — sqlite-wasm + OPFS

### 2.1 Why SQLite WASM

The server search service (`web/app/search_service.py`) is already SQLite + FTS5. Replicating that engine in the browser means:

- Zero query-translation layer — the same SQL runs client-side.
- FTS5 is built into the official `sqlite.org/wasm` distribution.
- External-content FTS5 tables are supported, keeping the pack compact (text stored once, not duplicated in the shadow table).

**Distribution**: `@sqlite.org/sqlite-wasm` npm package; alternatively download the JSWASM amalgamation from `sqlite.org/wasm` and self-host under `/static/wasm/`.

### 2.2 Storage backend — OPFS

Origin Private File System (OPFS) is the correct durable-storage VFS for production:

- Survives browser restarts.
- Not subject to LRU eviction (unlike Cache API).
- Hidden from the user's file picker; no cross-origin access.

**Worker requirement**: the synchronous OPFS VFS (`opfs-sahara`) requires a dedicated worker. The main thread communicates via `SharedArrayBuffer` (SAB). Requires the page to be served with:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

These headers must be added to the FastAPI middleware for any page that loads the search worker.

### 2.3 Fallback matrix

| Environment | Storage | Notes |
|---|---|---|
| Chrome/Edge ≥ 102, Firefox ≥ 111 | OPFS (sync) | Full support |
| Safari ≥ 17 | OPFS (async) | No sync VFS; use async OPFS wrapper |
| No SAB (cross-origin isolation missing) | OPFS async | Slower, still durable |
| No OPFS (old browser) | Memory (`memvfs`) | Pack lost on tab close; warn user |
| No WASM | — | Redirect to server search; log graceful-fail |

The search worker detects the available VFS at `init()` time and reports it via a status message.

## 3. Pack format

### 3.1 Separate offline DB (not a slice of corpus.db)

The offline pack is a **purpose-built SQLite database**, generated by a build script (`scripts/build_offline_pack.py`). It is not a copy or slice of `corpus.db`. This is necessary because:

- `corpus.db` includes HTML (121 MB) that is useless offline — the HTML is already cached as full page responses in the reader.
- FTS5 shadow tables in `corpus.db` are optimised for the server's Python query path, not for the WASM footprint.
- The pack schema can be versioned and evolved independently of the server DB schema.

### 3.2 Pack schema

```sql
-- Corpus metadata
CREATE TABLE pack_meta (
    key   TEXT PRIMARY KEY,
    value TEXT
);
-- key=corpus_version  → matches corpus_meta.corpus_version on server
-- key=pack_version    → semver of pack format itself
-- key=built_at        → ISO-8601 UTC
-- key=sha256          → SHA-256 hex of this file (self-referential, computed at build time)
-- key=source_count    → number of sources included
-- key=row_count       → total rows in corpus_lines

-- Sources included in this pack
CREATE TABLE pack_sources (
    source_id   INTEGER PRIMARY KEY,
    source_slug TEXT NOT NULL,
    title       TEXT NOT NULL,
    role        TEXT NOT NULL   -- 'translation'/'commentary'/'anthology'/'dictionary'
);

-- Text content (no HTML)
CREATE TABLE corpus_lines (
    id           INTEGER PRIMARY KEY,
    source_id    INTEGER NOT NULL REFERENCES pack_sources(source_id),
    link_id      TEXT NOT NULL,
    canonical_id TEXT,          -- e.g. 'SM_1_1#sa'
    chapter      TEXT,
    line_num     INTEGER,
    line_text    TEXT NOT NULL  -- plain text, same as corpus_lines.line_text on server
);
CREATE INDEX corpus_lines_source ON corpus_lines (source_id);
CREATE INDEX corpus_lines_link   ON corpus_lines (link_id);

-- External-content FTS5 table (no duplication of line_text)
CREATE VIRTUAL TABLE corpus_fts USING fts5(
    line_text,
    content='corpus_lines',
    content_rowid='id',
    tokenize='unicode61 remove_diacritics 0'
);
```

`remove_diacritics 0` is critical: IAST diacritics (ā, ī, ṭ, ṣ…) must be preserved in the index. Folding them would break SLP1-to-Unicode searches.

### 3.3 Pack variants (base vs dict)

**Corpus.db size breakdown (server, 2026-06-13):**

| Segment | Rows | Text size |
|---|---|---|
| Other (commentary, dict) | 408,571 | — |
| #ru (Russian translations) | 88,148 | — |
| #sa (Sanskrit passages) | 78,220 | — |
| **MW dictionary alone** | 222,390 | 52.9 MB |
| **Apte dictionary alone** | 31,647 | 16.1 MB |

MW + Apte together ≈ 75 MB of text. Excluding them from the base pack:

| Pack | Contents | Estimated size |
|---|---|---|
| **base** | All corpus sources except MW + Apte | ≤ 120 MB |
| **dict-add-on** | MW + Apte only | ≤ 75 MB |

The base pack covers all translations, commentaries, anthologies, and smaller dictionaries. The dict add-on is optional; the user downloads it separately in the Settings / Offline panel.

Pack sizes are compressed FTS5-optimised SQLite, not raw text. Actual wasm heap during query peaks at ~64 MB for the base pack (FTS5 loads B-tree pages on demand).

## 4. Query parity matrix

| Mode | Server | Offline | Notes |
|---|---|---|---|
| Plain (FTS5 match) | ✅ | ✅ | `corpus_fts MATCH ?` |
| Case-sensitive | ✅ | ✅ | Post-filter `GLOB` or `LIKE BINARY` |
| Whole-word | ✅ | ✅ | FTS5 phrase `"^word"` or post-filter |
| Regex | ✅ | ✅ | SQLite REGEXP via WASM user function |
| SLP1 / Roman transliteration | ✅ | ✅ | Convert query to Unicode before FTS5 |
| Morphological (stem) | ✅ | ❌ | Python UDPipe — network-only; show message |

Regex in WASM: SQLite does not include a REGEXP function by default. Register one via the `createFunction` API:

```javascript
db.createFunction('regexp', (pattern, str) => {
    const re = new RegExp(pattern, 'u');
    return re.test(str) ? 1 : 0;
});
```

The regex full-table scan has the same 1 M-row / 5 s guardrail as the server path — implemented by `LIMIT` + a JS `Date.now()` watchdog wrapping iterated `step()` calls.

## 5. Component architecture

```
Main thread                   Dedicated worker (search.worker.js)
────────────────              ──────────────────────────────────────────
offline.js (Phase 2)          sqlite-wasm (OPFS VFS or memvfs)
  registerOffline()    ──►    openPack(packType)   → 'ready'
  removeOffline()      ──►    closePack()
  listOffline()        ──►    listPacks()

search-offline.js     ──►    query(params)         → {hits[], took_ms}
  searchOffline()             (FTS5 → filter → format)
  isSearchAvailable()  ──►    status()              → {vfs, packs, version}
```

### 5.1 Message protocol (postMessage, structured clone)

All messages are plain objects: `{ type: string, id: string, payload: any }`. Responses: `{ type: 'reply', id, ok: bool, result | error }`. The worker wraps all DB operations in try/catch and always sends a reply.

### 5.2 New JS files

| File | Purpose |
|---|---|
| `web/static/scripts/search.worker.js` | Dedicated worker; owns sqlite-wasm instance |
| `web/static/scripts/search-offline.js` | Main-thread ES module; wraps worker postMessage |
| `web/static/wasm/sqlite3.wasm` | Self-hosted WASM binary |
| `web/static/wasm/sqlite3.mjs` | sqlite-wasm JS glue |

`search-offline.js` extends (does not replace) `offline.js`. The Phase 2 `offline.js` module remains the authority for page-caching and registry; `search-offline.js` adds the DB pack lifecycle on top.

### 5.3 Pack download and installation

```javascript
// search-offline.js
export async function installPack(packType = 'base', onProgress) {
    // 1. Fetch HEAD /offline-packs/{packType}.db → get Content-Length + ETag
    // 2. Stream-download with fetch() + ReadableStream, report progress via onProgress(pct)
    // 3. Accumulate ArrayBuffer chunks; verify SHA-256 (Web Crypto API)
    // 4. Write to OPFS via FileSystemFileHandle.createWritable()
    // 5. Open via sqlite-wasm opfs VFS, validate pack_meta.corpus_version
    // 6. Register in samudra-offline-registry under key 'pack:{packType}'
}

export async function removePack(packType = 'base') {
    // 1. Close DB if open
    // 2. Delete OPFS file via FileSystemDirectoryHandle.removeEntry()
    // 3. Remove from registry
}
```

The pack endpoint (`GET /offline-packs/{pack_type}.db`) is served as a static file from a dedicated directory, **not** derived from corpus.db at request time. The build script regenerates it when corpus_version changes. The endpoint must **not** be a public download link with a stable URL — it is served only from the app origin, behind the same auth surface as other assets.

## 6. Version sync and integrity

### 6.1 Version key

`corpus_meta.corpus_version` (server-side, stored in corpus.db) is the canonical version token. The pack embeds it in `pack_meta(key='corpus_version')`.

On each SW `activate` event (and on `search-offline.js` init), the worker fetches:

```
GET /api/corpus-version   →  { corpus_version: "20260613-001", pack_sha256: { base: "…", dict: "…" } }
```

If the stored pack's `corpus_version` differs, the UI shows a "Pack update available" notification (non-blocking). Auto-update is not performed — the pack is large.

### 6.2 Integrity check

SHA-256 of the downloaded file is verified client-side using `crypto.subtle.digest('SHA-256', buffer)` before writing to OPFS. The expected hash comes from the `/api/corpus-version` response (served over HTTPS).

### 7.1 Search page (`index.html`) — IMPLEMENTED (Phase 3e, see §12.7)

Existing flow: user types query → `search.js` POSTs to `/api/search` → results rendered.

1. A `window.SamudraOffline` bridge module (`offline-search-bridge.js`) is loaded;

## 8. COOP / COEP headers

SharedArrayBuffer requires cross-origin isolation. Add to `main.py` FastAPI middleware:

```python
@app.middleware("http")
async def coop_coep_headers(request, call_next):
    response = await call_next(request)
    # Only set on HTML pages, not on static assets (avoids breaking CDN CORS)
    ct = response.headers.get("content-type", "")
    if "text/html" in ct:
        response.headers["Cross-Origin-Opener-Policy"] = "same-origin"
        response.headers["Cross-Origin-Embedder-Policy"] = "require-corp"
    return response
```

woff2 fonts served from `/static/fonts/` must include `Cross-Origin-Resource-Policy: same-origin` so COEP doesn't block them. Add this header in the static file mount or the SW's `fetch` handler.

## 11. Out of scope for Phase 3

- **Morphological offline search** — UDPipe model is 50 MB+ additional payload; deferred to Phase 4 or permanently network-only.
- **Shared corpus packs between users** — packs live in the user's own OPFS; no server-side per-user state beyond the pack files themselves.
- **Public corpus download endpoint** — the pack endpoint serves the app's own static assets. No Zenodo/DOI/TEI export. See rights guardrail in session notes.
- **iOS installation on Safari < 17** — no OPFS before 17; memory-only fallback is the floor.

## 12. Phase 3d implementation findings (2026-06-13) — corrections to the spec above

Browser-verified end-to-end in Chrome against `@sqlite.org/sqlite-wasm` 3.53.0.
The following supersede the pre-implementation assumptions in §2 and §8.

### 12.1 Storage VFS — `opfs-sahpool`, not `OpfsDb`

§2.2/§2.3 assumed the regular OPFS VFS (`sqlite3.oo1.OpfsDb`) would be available
on a cross-origin-isolated page, with an "async OPFS" fallback when SAB is
absent. **Both assumptions were wrong for this build:**

- `sqlite3.opfs` is `undefined` even on a cross-origin-isolated page (the async
  proxy VFS does not come up). `OpfsDb` is therefore unusable here.
- The durable VFS that *does* work is the **OPFS SAH Pool**
  (`sqlite3.installOpfsSAHPoolVfs()` → `pool.OpfsSAHPoolDb`). It uses synchronous
  access handles, is durable across sessions, and — importantly — needs **no
  cross-origin isolation at all**. So the "no-SAB → async OPFS" row in the §2.3
  matrix is replaced by: *any browser with `FileSystemSyncAccessHandle` →
  opfs-sahpool (durable); otherwise → memory.*

Packs are placed in the pool with `pool.importDb('/samudra-{type}.db', bytes)`
and opened with `new pool.OpfsSAHPoolDb('/samudra-{type}.db')`. The main thread
no longer touches OPFS directly; it streams + verifies the download, then hands
the bytes to the worker as a transferable ArrayBuffer.

**Consequence for §7.1 (main-page offline search):** because sahpool needs no
COEP, offline search can run on `index.html` *without* enabling global COEP
(which would break Google Fonts). This removes the architectural blocker for the
main-page offline pill + routing — deferred to a later phase, but now unblocked.

### 12.2 Worker loading — three hard requirements

Loading the search worker from a COEP page required all three of:

1. **`.mjs` served as `text/javascript`** — Windows' registry has no `.mjs`
   entry; without `mimetypes.add_type` the glue is `application/octet-stream`
   and the dynamic import fails.
2. **Dynamic `import()` of sqlite3.mjs inside the worker**, never a static
   top-level import — a static import makes the glue a load-time dependency and
   the worker module fails instantiation with a detail-less `error` event.
3. **The worker script response must carry BOTH `Cross-Origin-Resource-Policy:
   same-origin` AND `Cross-Origin-Embedder-Policy: require-corp`** — a
   cross-origin-isolated document can only spawn a dedicated worker whose own
   top-level script asserts COEP. CORP alone is insufficient. The middleware now
   sets both on all `/static/*` responses (COEP is ignored for ordinary
   `<script>`/CSS/font loads, so this is safe for the non-isolated index.html).

The earlier "worker error: [object Event]" was the symptom of (2)+(3) together;
the MIME fix (1) was necessary but not sufficient.

### 12.3 Pack integrity — no self-referential hash

§3.2 listed a `pack_meta.sha256` "self-referential" key. That is impossible: a
file cannot contain its own hash, and the build script's post-hash reopen to
write it mutated the file *after* the sidecar SHA was computed, so every client
install failed SHA-256 verification. The `sha256` key is removed; the SHA lives
only in the `.db.sha256` sidecar, computed once on the final file (after a
`wal_checkpoint(TRUNCATE)` + `journal_mode=DELETE` so the on-disk bytes are
stable). The client verifies downloaded bytes against the sidecar.

### 12.4 Pack sizes + gzip-on-wire (RESOLVED — D1 option 1)

Real build, corpus `v2026.06.13`. The §3.3 estimate (base ≤120 MB) was ~70% low,
so packs are served **gzip-on-wire**: the build writes a deterministic
`{type}.db.gz` (gzip level 6, `mtime=0`); the endpoint serves it with
`Content-Encoding: gzip`; the browser decodes transparently so the client SHA-256
still matches the raw-`.db` sidecar, and `importDb` receives raw SQLite bytes. The
size gate now measures the **wire** (`.gz`) size.

| Pack | Rows | Raw (OPFS) | **Wire (gated)** | Gate | Status |
|---|---|---|---|---|---|
| base | 320,902 | 206 MB | **79 MB** | 130 MB | ✅ ships |
| dict | 254,037 | 88 MB | **38 MB** | 90 MB | ✅ ships |

Mechanics, all browser-verified:
- **Progress denominator** — under `Content-Encoding: gzip`, `Content-Length` is
  the *compressed* size while the fetch reader yields *decoded* bytes, so a
  byte-counting bar would overshoot. The raw decoded size is conveyed two ways:
  `pack_bytes:{base,dict}` in `/api/corpus-version` (primary — proxy-safe, already
  fetched) and an `X-Db-Bytes` response header (fallback — consistent with the
  served bytes). Client precedence: `pack_bytes` → `X-Db-Bytes` → `Content-Length`
  (only when not encoded) → indeterminate.
- **Integrity** — SHA-256 stays over the raw `.db` (never the `.gz`); fail-closed
  if the hash is unavailable. Worst case of any gzip mishandling is a SHA mismatch
  (fail-closed), not silent corruption.
- **Range footgun** — the gzip artifact is served via `StreamingResponse`, not
  `FileResponse`. FileResponse honours an inbound `Range` header and would return
  a 206 byte-slice computed over the *compressed* `.gz` while still setting
  `Content-Encoding: gzip` — an undecodable partial gzip. (Setting
  `Accept-Ranges: none` does *not* prevent this: Starlette decides 206 from the
  request's Range header, not the advertised value.) StreamingResponse has no
  range handling, so a Range request just gets the full 200 body. Verified: a
  `Range: bytes=0-1023` request returns 200 with the full, sidecar-matching body.
- **Crash-safe build** — the build writes `.db`/`.gz`/`.sha256` to temp files and
  atomically swaps them in, removing the real sidecar first and writing it last
  (commit marker). An interrupted rebuild never destroys the working pack and
  never yields a `.gz` whose decoded bytes disagree with the sidecar — which
  could otherwise either fail-closed forever or silently install stale-corpus
  content that still passes SHA. Every crash window degrades to fail-closed.
- **nginx** — `deploy/samudra.nginx` has a dedicated `location /api/offline-packs/`
  with `gzip off` (never double-compress) and large-download timeouts; the
  `/static/` block now replicates CORP+COEP (it bypasses the FastAPI middleware,
  which would otherwise break worker loading in production).

**Caveat:** gzip fixes the download, not the on-disk OPFS footprint (base is still
206 MB in user storage). A base-core/commentary split (D1 option 2) remains
available if low-end-device storage becomes a concern.

### 12.5 Client-side regex needs streaming, not materialisation

The worker's regex path used `db.selectObjects(sql)`, which materialises the
ENTIRE table into a JS array before the 5 s watchdog loop runs — ≈16 s for the
320k-row base pack, so the budget tripped on the first iteration and regex search
always returned 0 on large packs. Fixed to stream via a prepared statement
(`stmt.step()`), fetching only `line_text` per row and building the full row
object solely on a match. Result on the dict pack: 5 hits in **70 ms** (was 0 in
7.8 s). FTS plain search was unaffected (it already `LIMIT`s the materialised set).

### 12.6 Worker cache-busting

`new Worker(url)` uses a worker-script cache that a soft reload does not refresh,
and `/static` is served `immutable` for 7 days in production — so a deployed
worker update would not reach users. The worker URL now carries
`?v=WORKER_VERSION` (a constant in `search-offline.js`). **Superseded by the D4
fix** (§12.8) — app JS now revalidates at every layer, so `?v=` is no longer
load-bearing (kept frozen as belt-and-suspenders).

### 12.8 Cache strategy so deploys reach users (D4 resolved)

App-JS staleness had three layers, all fixed:
- **HTTP**: app JS/CSS served `Cache-Control: no-cache` (revalidate → 304 when
  unchanged, fresh on change); vendored `/static/wasm/` + fonts get 1-year
  `immutable`. Set in the FastAPI middleware (dev/Docker) AND `deploy/samudra.nginx`
  (prod bypasses the app: a regex location for binaries + the prefix location for
  app code).
- **Service worker**: was cache-first for ALL `/static/` (serves stale app code
  forever — it sits in front of the HTTP cache). App code now uses
  stale-while-revalidate; only `/static/{wasm,fonts,icons}/` stay cache-first.
- **`/sw.js`** served `no-cache`.
- **Pre-existing PWA bug fixed**: `PRECACHE_URLS` contained `/sources` (404s),
  and `cache.addAll` is all-or-nothing, so the SW install always failed and the
  PWA never worked offline. Removed the URL; install now uses
  `Promise.allSettled` + per-URL `cache.add` so one bad entry can't break it.

### 12.7 Main-page offline search (Phase 3e — D2 resolved)

Browser-verified that the worker loads and `opfs-sahpool` works on `index.html`
(NOT cross-origin isolated) — a pack installed on `/offline-settings` is
queryable from the main page, confirming `opfs-sahpool` needs no isolation.

- `offline-search-bridge.js` bridges the jQuery `search.js` (classic script) to
  the ES-module `search-offline.js`, exposing `window.SamudraOffline`. Lazy init
  (worker spins up on the `offline` event / first offline search). Searches
  across all installed packs and merges. Resolves source titles via
  `listSources` (rows carry only `source_id`). Renderer is a clearly-marked,
  degraded plain-text list — packs have no HTML — with query highlighting (on
  HTML-escaped text, no XSS) and reader links that work offline iff the source
  page was cached (Phase 2).
- `search.js` routes to the bridge only when `navigator.onLine === false` — the
  online `/api/search` path is byte-identical. Plus a network-status pill and a
  network-only message for morphological mode offline.
- Cache-busting (`?v=`) is applied to `search.js`, the bridge, and the bridge's
  import of `search-offline.js` — without it a browser-cached old module silently
  breaks the wiring (hit twice during dev: a stale `search.js` left the pill
  blank; a stale `search-offline.js` lacked `listSources` so titles fell back to
  "Источник N"). This is the D4 issue in miniature.
